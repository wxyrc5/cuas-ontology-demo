# 设计态—运行态混合引擎与数字线程

## 1. 为什么必须分层

OWL 2 DL/HermiT 适合验证 TBox/ABox 是否可满足、分类和互斥约束是否成立；它不应被放进亚秒或数秒级战术事件的每次判定路径。SWRL 适合表达可交换的设计规则，但开放世界假设、推理复杂度与工具实现差异不适合作为当前演示的实时执行承诺。

因此，本项目采用三段式结构：

1. **设计态**：OWL 2 DL + SHACL + SWRL。HermiT 做正向可满足性与负向互斥对照；SHACL 做字段、值域、基数和关系方向校验；SWRL 保存规则语义。
2. **构建态**：将已校验的 Object/Link、值域、指标阈值和规则前件物化为 JSON/SPARQL 资产；版本号和 SHA-256 进入证据链。
3. **运行态**：事件解码与规范化→闭世界 SPARQL/确定性谓词→Action JSON Schema→自动副作用或人工授权→Effect/EffectMetric 回写。运行时不调用 HermiT。

## 2. 运行态 Action 形式

每个 Action 至少包含：

| 字段 | 含义 |
|---|---|
| action_id / action_code | 稳定标识与动作类型 |
| preconditions | 触发规则、观测值与门槛 |
| target_mission / capabilities / equipment | 作用对象 |
| side_effects | 可见的状态变化；人工授权前必须为 none |
| validation_function | 动作执行后的机器可检查条件 |
| expected_revision | 乐观并发控制版本 |
| execution_status | AUTO_APPLIED 或 PENDING_HUMAN_AUTHORIZATION |
| evidence_refs | 规则、指标或查询证据引用 |

Schema 文件是 `03_源码/streamlit_app/data/action_contract.schema.json`。验证器同时运行正向样例和“删除 validation_function”的负向对照。

## 3. 边缘语义数据漏斗

输入包络定义在 `streaming_semantic_contract.json`，其最小字段为 source/event ID、事件/接收 UTC、CRS、WKT、精度、ENU 速度、Signal 元数据与观测负载。建议的边缘算子链为：

`JSON/Protobuf 解码 → Schema/时间检查 → 坐标与单位归一 → Object/Link 物化 → 闭世界触发 → Action 契约 → 人工授权 → Effect/Metric 回写`

该契约可承接未来 SAPIENT ASM 适配器、Kafka/Flink 总线或装备厂商协议，但本提交包只实现平台中立的公开数据模拟。没有连接 Palantir Foundry、真实实时总线或实装装备。

## 4. 数字线程

本项目的数字线程由七类可追溯对象串联：

`SourceEvent → SpatiotemporalContext/Signal/Threat → Mission Subgraph → RuleEvaluation → Action → Effect/EffectMetric → Notebook/Acceptance Hash`

其可审计性来自：

- 每个运行态 Action 有确定性 `decision_id`、版本与证据引用；
- 正式 TBox/ABox 只读，Action 写回输出为独立 RDF 预览；
- Notebook 输出、指标裁决、前端快照与发布清单采用同源指标并记录哈希；
- 失败工况（雷达失效、竞争链路、人工逐目标授权、效应器容量不足）不能被平均值隐藏。

## 5. 性能声明边界

当前可以声明：当前 ABox 上的 SPARQL 查询代码路径可测；Streamlit Action 引擎是确定性本地实现；完整 OODA 参数化模型显式计入传感、通信、关联识别、人工授权、瞄准、效应传递和反馈。

当前不能声明：5000+ 三元组的通用毫秒级保证；Drools/Flink/Jena SHACL-AF 已部署；SAPIENT ASM 已接入；真实竞争链路、人工席位、射界或效应器已台架标定。
